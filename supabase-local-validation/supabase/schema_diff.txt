4) Index differences (sample):
- SUPABASE_INIT.sql defines many explicit indexes with PascalCase names (e.g. "Product_sku_key", "Category_slug_key").
- Migrations define indexes with snake_case names (e.g. products_sku_key, categories_slug_key) and some additional indexes (is_active, sort_order combos).
- Some indexes or unique constraints exist in one and not the other (e.g. ProductVariant_sku_key in INIT vs ProductVariant not present in migrations).

5) Foreign key semantics differences
- SUPABASE_INIT.sql: FK definitions mostly use ON DELETE RESTRICT (seen in script), but some tables reference others via camelCase names.
- migrations: 0001_init initially had products.category_id REFERENCES public.categories(id) ON DELETE SET NULL (in one file), then phase4 explicitly changes to ON DELETE RESTRICT. There's a timing/order difference: INIT shows ON DELETE RESTRICT already.
- FK references in migrations often use `auth.users(id)` for profiles while INIT models users separately.

Summary (short):
- The migrations tree is focused on public.* snake_case schema, incremental, includes triggers and policies and seeds; it's the active incremental history.
- `SUPABASE_INIT.sql` is a larger monolithic snapshot including many additional domain tables (orders/payments/etc) and using PascalCase naming. They are not in sync; there are many naming and structural mismatches.
